## 1. 为什么三处必须一起重签（以及一个实测发现）

| 层 | 谁在用 | 只重签 manifest 会怎样 |
|---|---|---|
| `packages/<pkg>/manifest.json` 的 `signature`（`over=manifest`） | 节点仓验签门、`build_seed`、运行目录安装 | —— |
| zip **内嵌**的 `manifest.json` 签名 | `declarative.install_zip → _verify_install_signature → check_install_signature`（`over=manifest`） | zip 里还是**失效的旧签名** ⇒ 商城安装路径验签失败 |
| `dist/<pkg>.zip.sig`（`over=archive`，`sign(sha256(zip))`） | `check_signature.py --only-dist`、发布链卫生校验 | `.sig` 与重新打包后的 zip 摘要不匹配 ⇒ ARCH_SIG_FAIL |

**实测发现（比任务背景更精确，值得记档）**：`check_install_signature`（`app/signatures.py:488-493`）在
「已签名但 **pubkey_b64 为空**」时，只要 `required=False`（`user_*` 就是 L2）就直接返回
`{ok: True, level: L2, "已签名但无公钥锚，按社区级（L2）降级"}` ——**不会**走到 512 行的 `ok=False`。
所以「只重签 manifest 不重打包」的坏处，只在**传了 trust_pubkey 的商城 L1 路径**（或 `core/*` L0）才会拒装；
裸 `install_zip(zip)` 不传锚时会**降级放行**。这也是为什么这个缺陷能在仓库里躺这么久没人炸。
本次回归测试按**商城 L1 口径**（`trust_pubkey=官方锚`）跑，与线上一致（见 §6）。
