# node.py 代码契约（v3）

> 日期：2026-10-30
> 适用：manifest v3 包。
> 一句话：**manifest 声明身份，node.py 只写行为。node.py 里出现任何"声明"，都是死代码。**

---

## 0. 为什么需要这份文档

v3 规格只管 manifest（数据契约），从没说过 `node.py` 该怎么写。结果是首个包变成了「**v3 manifest + v2 代码**」的混合体，而作者无法判断哪部分代码是活的。

本文档由**实测**得出，不是设计推演。所有"禁止"都附失效现场。

---

## 1. node.py 的完整形状

一个 v3 包的全部代码就是这些：

```python
"""字幕装配节点：将 ASR 字幕 + 样式参数合成为样式化字幕。"""
from __future__ import annotations

from typing import Any, Dict

from app.nodespec import NodeBase


class SubtitleComposeNode(NodeBase):
    async def setup(self, ctx):
        """可选。加载模型、建目录等一次性初始化。不放就视为无初始化。"""
        return None

    async def run(self, ctx, inputs, params) -> Dict[str, Any]:
        sub = inputs.get("subtitle")
        preset = params.get("preset") or "默认"
        size = params.get("size", 48)
        # ... 业务逻辑 ...
        return {"styled_subtitle": result}
```

**就这些。** 没有 `spec()`，没有 `@register`，没有 `sys.path`。

### 反例（v2 模板的样子，v3 里全是死代码）

```python
from app.registry import register          # ← 死 import，且危险（见 §2.2）

class SubtitleComposeNode(NodeBase):
    @classmethod
    def spec(cls) -> NodeSpec:             # ← 死代码，平台不读（见 §2.1）
        return NodeSpec(type_id="core/subtitle_compose", inputs=[...], ...)

    def run(self, ctx, inputs, params):    # ← 缺 async
        ...
```

## 2. 禁止项（每条都有失效现场）

### 2.1 禁止写 `spec()`

**现象**：写了不生效，但没人知道。

**证据**：`backend/app/declarative.py:526-580` 的 `_make_python_class` 造出的类里：

```python
class _P(NodeBase):
    @classmethod
    def spec(cls) -> NodeSpec:
        return _spec_from_manifest(manifest)   # ← 覆盖插件自己的 spec()
```

**实测**：把 `core_subtitle_compose/node.py` 的 `spec()` 整段删掉，重新加载，`type_id / title / category / description / version / gpu_* / streaming / inputs / outputs / params` **11 个字段逐个比对完全相同**。

**后果**：`plugin-development-spec.md:165` 曾要求「`spec()` 应与 manifest 一一对应」，`:277` 要求「Python 的 spec 与 manifest 同步」——这让 96 个包的作者维护一份平台从不读的副本。**改 manifest 忘了改 `spec()`，不会有任何检查拦住你，也不会有任何后果**；反过来，改了 `spec()` 以为契约变了，更是错的。

### 2.2 禁止 `@register`（连 import 都别留）

**现象**：同一个节点在 `/api/specs` 出现**两条**。

**证据**：`backend/app/registry.py:34`：

```python
def register(cls):
    spec = cls.spec()
    _REGISTRY[spec.type_id] = cls    # ← 塞 A 表
```

而 `registry.py:70`：

```python
def list_specs():
    return [cls.spec() for cls in _REGISTRY.values()] + declarative.list_specs()  # ← A 表 + B 表
```

v3 包走声明式路径，注册在 `declarative._decl`（B 表）。用了 `@register` 就同时进 A 表，**两处相加 = 一个节点两个 spec**。

**注意**：`register()` 内部还会调 `cls.spec()`——如果此时 `spec()` 还是 v2 形状（`type_id` 硬编码），A 表里存的是一个**和 manifest 脱钩的副本**。

**做法**：`from app.registry import register` 这行也删掉。留着会让人以为要用。

### 2.3 禁止操作 `sys.path`

**现象**：依赖变成不可审计的。

**证据**：归档里 5 个包在顶部写 `sys.path.insert(0, _PKG_DIR)`，其中 `user_jsm_remake_draft/node.py:54` 插的是**别的包**的目录：

```python
if _CORE_DRAFT_PKG and _CORE_DRAFT_PKG not in sys.path:
    sys.path.insert(0, _CORE_DRAFT_PKG)
```

**后果**：它依赖 `core/draft_export`，但代码里那些裸名 import 是不是都来自这个依赖，**静态判断不出来**。`sys.path` 把「依赖」从可审计的清单变成了「运行时碰巧能 import 到」。

平台的 `_isolated_sys_path`（`declarative.py:257-286`）会兜住——但那正是问题：**兜底让错误静默通过**。

**判据**：**路径进不进 `sys.path`，由 manifest 决定（`deps`），不由代码决定。**

**平台怎么发现有人违反**：`_isolated_sys_path`（`declarative.py:257-286`）在退出时会把 `sys.path` 按快照复原。
如果复原前后不一致，说明这个包改过它——**这一刻可以报一条 WARN**，而不是静默复原。
现在它只是复原，不记录；建议加一条带包名的告警，让违规可见。

> 一条禁令如果没有检测手段，它就不是禁令，是建议。这正是本章存在的理由。

### 2.4 包内子模块用相对 import

```python
from . import schema          # 对
import schema                 # 错（依赖 sys.path）
```

## 3. 身份与行为的边界

| 归属 | 内容 | 出现位置 |
|---|---|---|
| **manifest 独有** | `id`、`version`、端口声明、参数声明、`perm`、`deps`、`exposable`、`runtime_hints` | manifest.json |
| **node.py 独有** | `setup()` / `run()` 的实现 | node.py |
| **重叠区（不可避免）** | 端口名、参数名的**引用**（`inputs["subtitle"]`、`params["preset"]`） | node.py |

**判据**：

- `id` 是身份，**不该出现在 node.py 里**
- 端口名、参数名会出现在 node.py，但那是**取值**，不是声明
- 业务类型（`SUBTITLE`/`AUDIO`）**不需要在 node.py 里引用**——类型检查由平台在连线和校验时做

### 引用不存在的参数会怎样

`params["preset"]` 而 manifest 没声明 `preset` → **`KeyError`**，运行时立刻暴露。

**这是正确的失败，不要提前校验。** 不需要写一个"静态扫描 node.py 里的字符串和 manifest 比对"的检查——那是过度工程，且扫描字符串会被变量名、拼接、条件分支骗过去。

### 输出契约：`return` 的键

引擎取输出的方式是**按 spec 遍历**，不是按你返回的字典遍历（`engine.py:982-1003`）：

```python
for spec_p in spec.outputs:
    val = outputs.get(spec_p.name)          # 只取 manifest 声明过的
missing_ports = [p.name for p in spec.outputs if ...]   # 只查"少给"
```

| 情况 | 后果 |
|---|---|
| 返回**多余的**键（manifest 没声明） | **静默丢弃**，不报错 |
| **少返回**了声明过的输出端口 | **报错**（`missing_ports`） |

判据：**`return` 的键必须覆盖 `manifest.outputs` 里的每一个 `name`。** v3 的 `outputs` 不允许写 `required`（V5），所以没有"可空输出"这回事——声明了就要给。

**多给不报错，不代表可以多给**：多余的键是死的，读代码的人会以为它有用。删端口时要扫三处——`manifest.outputs`、`spec()`（如果还留着）、`return` 的字典。

### 删了东西要扫全文

`report` 端口的真实案例（2026-10-30，`core/subtitle_compose`）：端口从 manifest 删了，但 `node.py` 仍然 `return {"styled_subtitle": out, "report": report}`，参数描述里仍写着"并在报告里标 degraded"。

引擎把它静默丢了，所以**不报错**——用户却会在向导里看到一个不存在的"报告"。**静默是最坏的失败方式：它让删了一半的东西看起来是完整的。**

删任何字段/端口后，用这个扫：

```bash
grep -rn "<被删的名字>" <包目录>/
```

## 4. ctx 契约（平台真正提供的）

`backend/app/nodespec.py:89-94`：

```python
async def run(self, ctx, inputs, params) -> Dict[str, Any]:
    """执行节点。ctx 包含: workdir, cache_dir, logger, cancel_event, progress(回调)"""
```

| key | 类型 | 用途 |
|---|---|---|
| `workdir` | str | 本次运行的工作目录 |
| `cache_dir` | str | 可复用的缓存目录（跨运行保留） |
| `logger` | Logger | 写日志 |
| `cancel_event` | Event | 长任务轮询它响应取消 |
| `progress` | callable | 上报进度 |

**没有 `ctx.report()`。** 诊断信息不要走端口（v3 已把 `JSON` 移出端口体系），也不新增接口——**要写诊断就用 `logger`，要留结构化数据就写 `workdir` 下的文件**。等第 2、3 个包都提出同一需求，再考虑正式接口。

### 资产

媒体/结构化资产一律经 `ctx` 的 store 存取，不要把文件路径当字符串传来传去。`Asset` 字段与 `AssetStore` 方法见 `plugin-development-spec.md`。

## 5. 自检（包作者用）

写完 node.py，跑这三条：

```bash
# 1. 有没有写 spec() / @register / sys.path（应该一个都没有）
grep -n "def spec\|@register\|from app.registry\|sys.path" node.py

# 2. 声明的方法是不是 async
grep -n "async def run\|async def setup" node.py

# 3. 包能不能被平台加载（这才是真判据）
cd FrameWeave/backend && python -c "
import sys, json; sys.path.insert(0,'.')
from app import declarative
m = json.load(open(r'<包目录>/manifest.json', encoding='utf-8'))
from app.plugin import manifest_v3
norm = manifest_v3.validate_manifest(m).manifest
cls = declarative._make_python_class(norm, r'<包目录>')
print('spec.id =', repr(cls.spec().type_id))
"
```

**第 3 条是唯一有意义的判据。** 前两条是代码卫生，第 3 条才证明"平台真的能装载它"。

> ⚠️ 截至本文档写作时，`manifest_v3` 尚不存在（平台仍只有 `manifest_v2`），第 3 条会失败。这是已知阻塞，见 `FrameWeave/docs/plans/v3落地阻塞与实施顺序_20261030.md`。在它修好之前，**任何 v3 包都只能说"符合规格"，不能说"能用"**。

---

## 6. 一句话总结

**manifest 是唯一的真源。node.py 里除了 `setup` / `run` 的方法体，任何"声明"都不是你的，而是平台从 manifest 生成的那一份的影子——影子不参与决策。**
